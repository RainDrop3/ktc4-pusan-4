AI는 세 곳에 있습니다: ① 에이전트 비서 Really, ② 판정하지 못한 지출의 규칙 카드 초안 생성(RAG), ③ 판정 전 가맹점 카테고리 분류. 세 곳 모두 "AI가 틀려도 틀린 판정이 나가지 않게" 만드는 것이 목표였고, 실험도 정확도 하나보다 틀린 채 통과하는 몫을 얼마나 줄이느냐를 봤습니다.

"AI가 규칙을 만들고, 규칙이 판정한다." AI의 출력은 언제나 사람이 확인하는 자리(제안 카드의 [적용], 관리자 검수, 분류 확인 화면)를 거칩니다.

LangChain 없이 직접 짠 루프와 Luna를 씁니다. 제안의 근거는 코드가 검사하고, 프롬프트 인젝션 7종을 막았습니다. 실험 2 (2026.09.21 ~ 10.26) 규칙 카드 생성 RAG 판정하지 못한 지출에 맞는 조문을 찾아 규칙 카드 초안을 쓸 수 있나? 기본 조문을 항상 붙이고 RRF 하이브리드로 검색한 뒤, Luna 에이전트 3단계가 초안을 씁니다. 사람이 승인해야 카드가 됩니다. 실험 3 (2026.09.06 ~ 11.01) 가맹점 카테고리 분류 상호 문자열만 보고 32개 카테고리를 맞힐 수 있나? 사전과 키워드룰로 확정하고, 남은 가맹점은 GPT-6 Luna가 후보 3개만 추천합니다. 자동 확정은 하지 않습니다.

실험 1 (2026.10.15 ~ 11.03)

에이전트 비서 Really

화면 오른쪽 아래 버튼으로 여는 대화형 비서입니다. 비서는 판정하지 않고, 사용자가 질문에 답하고, 판정을 이해하고, 세무대리인에게 넘기는 일을 돕습니다. 데이터를 바꾸는 일은 제안 카드로만 만들고, 사용자가 [적용]을 눌러야 기존 API로 실행됩니다.

실험은 두 갈래였습니다. 하나는 무엇으로 만들지(프레임워크와 모델, 10.15), 다른 하나는 얼마나 안전한지(프롬프트 인젝션과 추가 공격, 11.02)입니다.

결론. LangChain 없이 openai SDK로 루프를 직접 짜고, 기본 모델은 GPT-6 Luna(예비 Claude Haiku 5.5)입니다. 모델이 틀릴 수 있는 곳은 코드가 지킵니다: 제안의 근거 검사(인용 대조, 날짜, 금액으로 대상 특정), 최종 답 검증(숫자, 조문, 말투), 즉시 거절 규칙. 프롬프트 인젝션 7종을 막았고, 지금 평가 시나리오 44건 중 42건이 통과합니다.

  1. 2026.10.15전제 확인
    캠퍼스 LLM 게이트웨이로 도구 호출 에이전트를 만들 수 있는지부터 확인했습니다
    • gpt-4o-mini와 GPT-6 Luna 모두 도구 선택과 인자가 정확했고, 도구 결과를 받은 뒤 답했습니다. 한 응답에 도구 2개를 부르는 병렬 호출과 strict 스키마도 통과했습니다. LLM 호출 1회는 1.1~2.2초였습니다.
    • Langfuse에 에이전트 → LLM 호출 → 도구 실행 트리가 모델, 토큰, 비용, 지연과 함께 남았습니다.

    • 대신해 주는 것이 작습니다. 에이전트 함수가 해 주는 일(모델 호출 → 도구 실행 → 결과 전달 반복)은 직접 짜도 15줄 정도입니다. 우리 코드의 대부분인 근거 검사, 별칭 변환, 화면별 도구 묶음, 제안 카드 수집, 최종 답 검증과 재시도는 LangChain을 써도 직접 짜야 합니다.
    • 추적이 두 번 기록됩니다(확인함). Langfuse가 openai 호출 메서드를 전역으로 감싸는데 LangChain도 같은 메서드를 불러, 콜백을 붙이면 같은 호출이 두 번 남습니다.
    • 고정 비용이 큽니다. 의존성 30개, 프로세스당 메모리 약 40 MB(AI 컨테이너 상한 512 MB). 대화 상태 저장 기능은 팀 삭제 정책 밖에 사용자 데이터를 만듭니다.
    • 다시 검토할 때: 여러 모델 공급자를 오가야 할 때, 서버가 긴 작업의 상태를 들고 있어야 할 때, 기성 통합을 그대로 쓸 때.
  3. 2026.10.15후보 고르기와 사전 확인 (Luna, Haiku 5.5, 6.1 Sol)
